# OpenSIPS GB28181 HA（无 MySQL/PG/Redis）实施计划

## Context

**为什么做这次改动**

`etc/opensips_proxy.cfg` 是一个 GB28181 SIP 信令代理，部署在设备和 EasyGBS 平台之间。**单点故障**：单进程 OpenSIPS 挂掉后所有设备/平台通信中断。

**既有的 HA 调研**（`docs/opensips_gb28181_proxy.md` 3.3 节）描述了 Keepalived + iptables + 每机独立 SQLite 的方案。它的不足：

- 节点 2 平时 SQLite 是空的，VIP 漂移后必须等设备主动重连 REGISTER 才能恢复
- **Catalog 子通道完全没考虑**：`route[process_catalog]` 直写 SQLite 不走 usrloc，节点 2 上子通道为零，故障切换后平台 INVITE 子通道全部 404

**用户约束**：节点规模 = 2（active/standby），**禁止使用 MySQL/PostgreSQL/Redis**。项目是 OpenSIPS 源码仓库（`/root/work/zf2zf/opensips/opensips`），自带 `clusterer` / `proto_bin` / `httpd` / `usrloc.full-sharing-cluster` / `dispatcher.by-shtag` 等必要能力。

**期望结果**：在不引入外部数据库的前提下，2 节点主备部署，故障切换后业务（设备主注册 + Catalog 子通道 + 平台转发）能在 10 秒内恢复，不依赖平台主动重查。

**完整设计文档**：`docs/superpowers/specs/2026-07-28-opensips-gb28181-ha-design.md`（已与用户对齐、已自审、用户已批准）。**本计划是该设计的精简执行版**。

---

## 关键设计决策（实施时锁定）

1. **2 节点 active/standby**，节点 2 平时不监听 SIP 5060（仅 BIN 5566 + HTTP 8080）
2. **配置文件 = 3 个纯 .cfg + `include_file`，不用 m4**
3. **两条同步通道**：
   - **BIN 通道**（clusterer）：usrloc + dispatcher 自动接管
   - **HTTP 通道**（httpd + json.so）：节点 1 主动重放**直写 SQLite** 的 JSON 到节点 2
4. **`usrloc.working_mode_preset = "full-sharing-cluster"`**（已查 `modules/usrloc/ul_mod.c:569` 确认合法）
5. **HTTP 角色随 HA 状态翻转**：active 节点 = HTTP client，standby 节点 = HTTP server。两节点都监听 8080，由 `$clustermode` 决定是否发请求
6. **HTTP body 是结构化 JSON**，不是裸 SQL
7. **兜底**：节点 2 缺数据时，401 触发设备重注册（已有逻辑，不变）

## 实施步骤（按顺序）

### Step 1：创建 `etc/opensips_proxy_ha.cfg`（主入口）

参考设计文档 §4.1 / §4.2 / §4.3 / §4.4 / §4.5 / §4.6 / §6.3。

关键内容：
- 全局参数（log_level、udp_workers=4 等，与 `opensips_proxy.cfg` 一致）
- `include_file "/etc/opensips/local.cfg"`
- `mpath`、`loadmodule` 顺序（**注意**：`proto_bin.so` / `clusterer.so` / `httpd.so` / `json.so` 在 DB 驱动之前；`json.so` 用于 `json_get_field`）
- usrloc modparam：`working_mode_preset=full-sharing-cluster`、`db_url=sqlite:///var/lib/opensips/opensips.db`、`use_domain=false`、`nat_bflag=NAT`、`location_cluster=1`、`skip_replicated_db_ops=0`
- dispatcher modparam：`cluster_id=1`、`cluster_sharing_tag=sip_active`、`cluster_probing_mode=by-shtag`、`ds_ping_from=VIP:5060`
- clusterer modparam：`db_url=sqlite:///var/lib/opensips/opensips.db`、`db_mode=1`、ping/timeout/sync 参数
- httpd modparam：`ip=本机IP`、`port=8080`（**由 `local.cfg.nodeX` 覆盖**）
- json.so 加载（无 modparam）
- `include_file "/etc/opensips/opensips_ha_routes.cfg"`
- `startup_route`：建 location 表 + `xlog("HA: startup on node $cluster.my_node_id (cluster_id=1)\n")`
- 4 个 `event_route[clusterer:...]`（仅日志）
- 1 个 `event_route[http:request]`（路由到 `route[replay_channel]`）

### Step 2：创建 `etc/opensips_ha_routes.cfg`（业务路由）

**基础** = 复制 `etc/opensips_proxy.cfg` 的 `route[maxfwd]` 之后的所有内容（94 行起）。

**改造 1：`route[process_catalog]`**（参考设计 §7.1）
- 在原 `sql_query("INSERT INTO location ...")` 之后追加：
  - `if ($clustermode == 1) { $var(peer_http) = "<peer_ip>:8080"; } else { $var(peer_http) = NULL; }`
  - 拼 `$var(repl_delete)` = `{"op":"delete","where":{"username":"<chan_id>"}}`
  - 拼 `$var(repl_insert)` = `{"op":"insert","row":{...}}`（username/domain/contact/expires/q/callid/cseq/last_modified/flags/user_agent/socket/attr）
  - 2 个 `http_async_query`（仅当 `$var(peer_http) != NULL`）

**改造 2：`route[register]` 注销分支**（参考设计 §7.2）
- 在原 `sql_query("DELETE FROM location WHERE attr LIKE '%' || '$tu' || '%'")` 之后追加：
  - 1 个 `http_async_query` 推 `{"op":"delete","where":{"attr_like":"%<tu>%"}}`（仅当 `$var(peer_http) != NULL`）

**新增：`route[replay_channel]`**（参考设计 §7.3，接收端）
- 校验 body 非空
- `json_get_field` 解析 `op` 字段
- 分支：`op=delete`（解析 `where.username` 或 `where.attr_like` → `sql_query` DELETE）、`op=insert`（解析 `row.*` 字段 → 拼 INSERT SQL → `sql_query`）
- 任意异常 → `$http_reply(400/403, ...)`
- 成功 → `$http_reply(200, "OK", ...)`

**改造 3：`route[check_keepalive]`**（参考设计 §6.4 "其余路由"）
- 在 401 返回前加一行 `xlog("L_WARN", "KEEPALIVE: device $var(device_id) NOT in local usrloc, may be sync gap or failover\n")`

### Step 5：端到端验证

参考设计 §10 验收方法，分 5 层验证：

1. **配置语法**：`opensips -f /etc/opensips/opensips_proxy_ha.cfg -c`（两节点各跑一次）
2. **启动层**：两节点 `systemctl start opensips`，观察日志 `HA: startup on node N` + clusterer 邻居 reachable + usrloc sync from donor
3. **同步层**：节点 1 `save("location")` 后，节点 2 SQLite 立即可见同一条记录
4. **故障切换层**：`ssh node1 systemctl stop opensips`，观察 VIP 漂移、节点 2 notify_master、OpenSIPS 重启、SIP 流量恢复
5. **边缘场景层**：
   - 节点 1 写完 SQLite 后立即 kill -9，节点 2 提为 active，子通道 404 触发设备重发 Catalog

## 风险（实施时需关注）

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| `working_mode_preset=full-sharing-cluster` 在 OpenSIPS < 2.4 不支持 | 项目 OpenSIPS 版本过低 | Step 1 前先 `opensips -V` 检查 ≥ 2.4 |
| `json_get_field` 函数签名 / 用法 | 第一次使用 | 实施时先查 `modules/json/README` |
| 设备 ID 含 `'` 或 UTF-8 字符破坏 JSON 拼接 | GB28181 设备 ID 偶发 | 实施时检查 `$avp(chan_id)` 替换 `'` 为 `\'` |
| `$clustermode` 伪变量在 OpenSIPS 中是否真存在 | 文档没明确写 | Step 1 之前查 `modules/clusterer/README`；若不存在，用 `clusterer_get_shtag_state` 替代 |
| `http_async_query` 在事件路由中可能丢请求 | 高频写场景 | 监控 httpd 队列深度；必要时降级为同步（但会阻塞） |
| 节点 1 写 SQLite + HTTP 推送**前**挂 | 极端时序 | 兜底是 401 触发重注册 |
| clusterer 启动时找不到 donor 卡 `sync_timeout=500` | 节点 1 还没启动 | 部署脚本先启动节点 1，等 `clusterer: neighbor reachable` 后再启动节点 2 |
